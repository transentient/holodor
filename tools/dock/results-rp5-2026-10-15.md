- stream 1 (371.087 s): hdmi_codec_hw_params -> msm_dp_audio_prepare -> engine ON; q6afe_dai_prepare -> q6afe_port_start
  -> SET_PARAM_V2 sent, response status 0 in 0.3 ms -> DEVICE_START sent 371.0874 -> NO RESPONSE -> -110 at 374.25 ->
  prepare fails (ASoC aborts; hdmi_codec_prepare never runs; is_port_started false so no STOP).
- stream 2 (384.619): shutdown of 1 (engine OFF), hw_params (engine ON), SET_PARAM_V2 sent 384.61964 -> at 384.62154
  a response arrives with payload opcode DEVICE_START status 0 = THE LATE ACK OF STREAM 1'S START (13.5 s late), 40 us
  later the SET_PARAM ack -> DEVICE_START sent 384.62161 -> NO RESPONSE -> -110 at 387.82.
- stream 3 (398.058): same prelude; the late ack of stream 2's START arrives 2 ms after SET_PARAM goes out; then
  DEVICE_START sent 398.0606 -> response status 0 at 398.0709 (10 ms) -> prepare OK -> hdmi_codec_prepare (engine ON
  again) -> tone plays; at close DEVICE_STOP acked in 3 ms.
Reading: the DSP executes every DEVICE_START (status 0) but the RESPONSE of a START that actually starts the port is
not delivered until the host's next command; the next stream's START is then issued against a port the DSP already
runs, and only the third stream (START on an already-running port, prompt ack) plays. The late ack arrives in the
same callback burst as the following command's ack (40 us apart) = a message sitting in the GLINK/APR receive path
until the next traffic (missed RX signal) OR a DSP-side gate released by the next command; the fs2 discriminator
(pro-audio profile, an unrelated speaker stream as the kick) separates the two. Codec/CPU ordering is correct (engine
ON before START). The staged 0720 (stop+start inside prepare) treated this symptom; the fix belongs in the transport
or in q6afe's response handling once fs2 names it.

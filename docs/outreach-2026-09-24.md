## READ FIRST: two of the three "msftdata" messages are on hold

The plan (HANDOFF 09-17 and 09-23, plan WP6, upstream sweep 09-24 item 8) says ROCKNIX's
`installtointernal` and MaSieS's `install-masios-to-internal.sh` "still type the internal
FAT msftdata", i.e. they would hit the Android bootloop we found on 09-17. Checking that
claim against the actual scripts and against parted's GPT behaviour says otherwise:

- ROCKNIX `projects/ROCKNIX/packages/rocknix/sources/scripts/installtointernal`
  (commit f15d4a06, 2026-09-17), lines 172-176:
  ```
  parted -a optimal -s "$DEVICE" mkpart primary fat32 "${RK_START_MB}MiB" "${RK_END_MB}MiB"
  parted -s "$DEVICE" name "$RK_NUM" ROCKNIX
  parted -s "$DEVICE" set "$RK_NUM" msftdata on
  parted -s "$DEVICE" set "$RK_NUM" boot on
  ```
- MaSieS `external-and-mods/ufs-install/install-masios-to-internal.sh` lines 574-577: the
  same four lines (`msftdata on` then `boot on`).
- On a GPT disk, parted's `boot` flag IS the ESP flag (the two names are one flag), and
  setting it rewrites the partition type GUID. Tested on fusor with parted 3.7 on a
  scratch image (`scratchpad/gpt-test.img`), reading the type back with `sgdisk -i`:
  ```
  after mkpart fat32:    EBD0A0A2-B9E5-4433-87C0-68B6B72699C7 (Microsoft basic data)
  after set msftdata on: EBD0A0A2-B9E5-4433-87C0-68B6B72699C7 (Microsoft basic data)
  after set boot on:     C12A7328-F81F-11D2-BA4B-00A0C93EC93B (EFI system partition)
  parted print:          ... ROCKNIX  boot, esp
  ```
  So both scripts END with an EFI System partition. The `msftdata on` line is dead code,
  not a bug. Our own pre-09-17 installer (commit 5056caa's parent) had only
  `mkpart fat32` + `name` — no `boot on` — which is why WE looped and they did not.
- UNVERIFIED on a real ROCKNIX / MaSieS internal install (parted on their images could
  behave differently only if it were older than 3.2, which is when `esp` became an alias
  of `boot`; ROCKNIX builds current parted). The check, from any Linux booted on such a
  device: `sgdisk -i <N> /dev/sda` for the ROCKNIX FAT partition. If it prints
  `EBD0A0A2...` the two held drafts become valid again as written.

Consequence: draft (a) to ROCKNIX and draft (c1) to MaSieS are HELD. Sending them would
tell two projects to fix something that is not broken. HANDOFF's "ROCKNIX still types the
FAT msftdata; nobody told them" line and plan WP6 need correcting (not done here: HANDOFF
is out of this task's scope). What remains worth sending: (b) to Armada about HOLODOR_ROOT
and (c2) to MaSieS about the Retroid Pocket 6 input.

## (a) ROCKNIX — HELD, do not send unless the on-device check above shows basic data

Where: new issue on https://github.com/ROCKNIX/distribution (or the ROCKNIX Discord's
dev channel, whichever Cliff prefers).

```
Title: installtointernal: internal FAT typed "Microsoft basic data" bootloops AYN Odin 3 Android

On the AYN Odin 3 (December 2025 Android), a FAT partition on the internal UFS typed
"Microsoft basic data" makes Android reset about 12 seconds into every boot. The same
partition typed "EFI System" boots, and Linux still boots from it. We bisected this on
the device; the partition name and contents do not matter, and the SD card's FAT is
harmless.

installtointernal (packages/rocknix/sources/scripts/installtointernal, lines 175-176)
sets the partition to msftdata:

  parted -s "$DEVICE" set "$RK_NUM" msftdata on
  parted -s "$DEVICE" set "$RK_NUM" boot on

Suggested change: drop the msftdata line and use

  parted -s "$DEVICE" set "$RK_NUM" esp on

Holodor's installer does this since 2026-09-17:
https://github.com/transentient/holodor/blob/main/docs/install-to-internal.md

Would you take a pull request for this?
```

Why held: with parted >= 3.2 the second line already produces EFI System (test above);
the message as written is wrong for their script.

## (b) Armada — send: installer and Holodor's partition names

Where: a NEW issue on https://github.com/armada-os/armada, not #350. #350 ("Odin 3
internal install hangs indefinitely at Starting Steam", opened 08-xx, second user
2026-09-23) is about their Steam start after an internal install; our finding is a
different subject and would derail their thread. The EFI-type finding itself is not
worth a message to Armada: their installer types its ESP EFI and never hit the loop
(HANDOFF 09-17).

Fact base (HANDOFF 09-22 "what we learned"): Armada's 20260907 release installer stops
with "unrecognized partition after userdata" when it finds HOLODOR_ROOT;
`system_files/usr/lib/armada/storage-lib` knows only userdata, ARMADA_ROOT and ROCKNIX;
their git main (4fadaea, 2026-09-23) replaces anything after userdata. Holodor's
installer replaces ARMADA_ROOT / ROCKNIX / STORAGE installs (docs/install-to-internal.md,
"Replace" mode, tested 09-17/18).

```
Title: Installer stops on a Holodor install (HOLODOR_ROOT after userdata)

Holodor is another Linux for the AYN Odin 3 (https://github.com/transentient/holodor).
On the internal UFS it uses the same layout as ROCKNIX and Armada: after userdata, a
boot FAT named HOLODOR and a root partition named HOLODOR_ROOT.

The Armada 20260907 installer stops with "unrecognized partition after userdata" when
these two exist, so a Holodor user has to reset the device with the ABL "uninstall CFW"
option before installing Armada. It looks like the current main branch replaces any
partitions after userdata instead.

Will that behaviour be in the next release, or should HOLODOR / HOLODOR_ROOT be added
to the known names? (Holodor's installer already replaces ARMADA_ROOT / ROCKNIX
installs the same way.)
```

### (c2) Retroid Pocket 6 has no controller — send, as a comment on issue #1

Where: https://github.com/MaSieS4Fun/SteamOS-ARM-SM8550/issues/1 ("wont launch on my
RP6"). Verified in their tree (docs/masies-sm8550-port-2026-09-24.md section 3 and 6):
`odin-overlay/etc/inputplumber/devices.d/02-ayn-odin.yaml` matches the devicetree
`model` only for "AYN Odin 2", "AYN Odin 2 Mini", "AYN Odin 2 Portal", "AYN Thor";
their RP6 DTS (`external-and-mods/kernel/patches/masi/qcs8550-retroidpocket-rp6.dts`
line 15) has `model = "Retroid Pocket 6"`, `compatible = "retroidpocket,rp6"`;
`odin-overlay/usr/lib/udev/rules.d/70-sm8550-gamepad.rules` hides the raw rsinput pad
from Steam; `odin-overlay/usr/share/steamos-manager/devices/ayn-odin2.toml` lists only
ayn,odin2 / odin2mini / odin2portal. So on an RP6 InputPlumber never builds the
virtual Steam Deck controller and Steam sees no pad at all.

```
I looked at the overlay for the RP6 problem.

etc/inputplumber/devices.d/02-ayn-odin.yaml only matches the device tree model
```
